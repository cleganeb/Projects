# Кейс: оцифровка нотных рукописей

Альтаир x «Школа 21». Партнёр — Оркестр Новосибирского государственного университета (@antonniyazov).
Постановка — `TZ_omr.docx` (это первоисточник; если этот README и ТЗ расходятся, верьте ТЗ).

За четыре проектных дня нужна не оркестровая партитура, а **работающий прототип на узком классе**: фото/скан простого (лучше одноголосного) фрагмента → символы → высота и минимально длительность → MIDI, по возможности MusicXML. Места с низкой уверенностью подсвечиваются.

Сбор полного датасета — работа команд. Здесь стартовые указатели, ограниченный список символов, два **неразмеченных** примера и заготовки для картинки/MIDI.

## Что нужно сделать

По ТЗ:

- посмотреть, какие особенности рукописей сильнее всего бьют по распознаванию;
- выровнять, поднять контраст, убрать шум;
- найти ноты и основные символы;
- восстановить высоту и в минимуме длительность;
- собрать последовательность и выгрузить MIDI;
- отметить неуверенные места;
- проверить на рукописях, которых не было в обучении, и разобрать типичные ошибки.

На защите — несколько новых рукописей, не только удачные кадры.

## Ограниченный набор символов (минимум)

Хватит, чтобы получить слушаемый MIDI с простого фрагмента:

| Символ | Обязателен в минимуме |
|---|---|
| нотный стан (5 линий) | да |
| скрипичный ключ | да; если детектор ключа не успели — явно зафиксировать «считаем treble» |
| заполненная головка | да |
| штиль | да |
| тактовая черта | желательно |
| пустая головка (половинка) | если успеете |
| пауза, диез/бемоль, ребро восьмых | после минимума |

Не ставить в минимум: аккорды, несколько голосов на одном стане, ключ F/C, орнаменты, динамику, 8va, текст, оркестровый счёт.

## Неразмеченные примеры

`data/unlabeled/` — две картинки **без** правильного MIDI, без JSON с ответом и без чужого разбора.

| файл | что это |
|---|---|
| `printed_fragment.png` | простой печатный одноголосный фрагмент |
| `handwritten_fragment.png` | обрезок рукописного стана (автограф, общественное достояние) |

Их не использовать как единственный train. Это вход, на котором на защите можно показать пайплайн. Ответ вы восстанавливаете сами.

## Инструменты, которые стоит потрогать самим

Готового разбора «Audiveris на этом файле выдал вот это» здесь нет — его надо получить у себя.

- [Audiveris](https://github.com/Audiveris/audiveris) — печатный OMR, Java. Batch: `audiveris -batch -transcribe -export -output out image.png`
- [oemer](https://github.com/BreezeWhite/oemer) — end-to-end, модели под печать; GPU желателен, на CPU медленно
- OpenCV + классика: проекция стана, морфология, шаблоны головок
- `music21` / `pretty_midi` / `mido` — MIDI и MusicXML

В `starter/` — только чтение картинки (в том числе с не-ASCII путём) и запись MIDI из списка нот. Детектора там нет.

```bash
pip install -r starter/requirements.txt
```

## Вопросы, без которых легко сделать вид, что «распозналось»

1. Чем почерк одного человека ломает детектор, обученный (или отлаженный) на другом?
2. Что делает с проекцией стана даже небольшой наклон страницы? А волнистые линии автографа?
3. Почему аккорд — это другой класс задачи, не «ещё одна головка»?
4. Если ключ не найден, какие высоты вы получите и как об этом сказать музыканту?
5. Что проще: высота по y относительно линий или длительность по рёбрам/флажкам/заливке?
6. Чем печать проще рукописи геометрически (линии, шаблоны, слияние штрихов)?
7. Когда автомат **не** экономит время: правка каши дольше, чем набрать фрагмент руками в MuseScore?

Исследовательская часть ТЗ: устойчивость к новому почерку и к качеству фото. Не только accuracy на своей выгрузке.

## Как будут смотреть результат

Критерии из ТЗ:

- качество обнаружения нот и символов;
- точность высоты и, если сделали, длительности;
- итоговое MIDI/последовательность против оригинала;
- корректность низкой уверенности (красное там, где правда сомнительно, а не случайный шум);
- сколько ручных правок остаётся музыканту после автомата.

Сильная версия — ещё и MusicXML, который открывается в нотном редакторе.
